# invoice-extractor

Extract structured data from free-text invoices into validated JSON, using the Gemini API and Pydantic, with a reproducible evaluation.

## What it does

Given the text of an invoice (formal layout, e-mail, compact line, English), it returns an `Invoice` object: number, issue and due date, supplier, VAT number, currency, line items and totals. If the model's answer is formed in a wrong way or the numbers do not add up, the tool reports an explicit error instead of a wrong record.

## Quickstart

```bash
uv sync
cp .env.example .env        # then put your Gemini API key in .env
uv run python extract_cli.py data/examples/case_00.txt
uv run python extract_cli.py data/examples/case_00.txt --prompt v1
```

Windows PowerShell: use `Copy-Item .env.example .env`. To read from standard input:
`Get-Content -Raw -Encoding utf8 file.txt | uv run python extract_cli.py -`

Exit code: `0` on success, `1` if the extraction failed.

## How it works

text -> prompt + JSON schema -> Gemini -> JSON string -> Pydantic validation -> `Invoice` or a classified error

- **Prompts as data** (`extractor.py`): `v1` zero-shot, `v2` with explicit rules and two worked examples.
- **Three levels of correctness**: valid JSON, valid schema, and semantic checks (line items sum to the net total, net + VAT equals the total, ISO currency code).
- **Two kinds of failure, kept apart**: `api` (infrastructure: network, quota) and `validation` (the model answered but the answer is invalid). Evaluation excludes API errors from the denominator.
- **Retries** with exponential backoff and jitter on transient errors (429, 500, 503). The SDK also retries internally, so attempts multiply.

## Evaluation

All documents are **synthetic** (generated by `make_testset.py` and `make_hard_testset.py` with fixed seeds), so the expected answer is known by construction.

- `data/testset.jsonl`: 20 cases, four layouts, mixed date and amount formats.
- `data/testset_hard.jsonl`: 40 cases with realistic noise (customer VAT number and fiscal code, delivery date, page break, IBAN, PEC).

Metrics: per-field accuracy, precision/recall/F1 on line items, perfect records (all fields right, no wrong or missing line), 95% Wilson interval, exact sign test for paired comparisons.

Results (gemini-3.5-flash-lite, temperature 0, one run):

| Prompt | Schema descriptions | Test set | Perfect records | 95% CI | Mean tokens (in / out) |
|---|---|---|---|---|---|
| v1 | yes | hard | 39/40 | 0,87–1,00 | 411 / 254 |
| v2 | yes | hard | 40/40 | 0,91–1,00 | 1089 / 252 |
| v1 | no | hard | 38/40 | 0,83–0,99 | 411 / 255 |
| v2 | no | hard | 40/40 | 0,91–1,00 | 1089/ 247 |

v2 scores 40/40 perfect records in both configurations; v1 scores 39/40 with schema descriptions and 38/40 without. The differences between the prompts are not statistically detectable (exact sign test: p = 1.0 with descriptions, p = 0.5 without). All three observed failures are the same error: a due date invented when the invoice has none and other dates are present. v1 made it in 3 of 80 evaluations, v2 in none, at about 2.6x the input tokens. Removing the schema descriptions made no measurable difference in this setup.

Reproduce:

```bash
uv run python make_testset.py
uv run python make_hard_testset.py
uv run python eval_extractor.py --testset data/testset_hard.jsonl --rpm 10
uv run python eval_extractor.py --testset data/testset_hard.jsonl --rpm 10 --no-descriptions
```

## Limitations

- Documents are synthetic and more regular than real invoices: these numbers are likely to **overestimate** real-world performance.
- Small test sets (20 and 40 cases), one model, one run; temperature 0 does not guarantee identical outputs.
- Input is plain text: no PDF or OCR handling.
- The model name may change over time; edit `MODEL` in `llm_client.py`.
- Sending real invoices to an external API raises data-protection questions that are out of scope here.
- The hard test set is too easy to separate the two prompts, and results are likely optimistic on real invoices.
